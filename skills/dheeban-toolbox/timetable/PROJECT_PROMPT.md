# برومبت دمج محرك الجداول — يلصقه المالك في جلسة المشروع الرسمية للنظام الإداري المدرسي

> اكتب بالعربية. هذا المشروع وحده: لا تلمس مستودعًا أو قاعدة بيانات أو خادمًا لمشروع آخر. عند أي شك توقّف واسأل المالك.

ادمج محرك الجداول المدرسية المبني على Google OR-Tools CP-SAT في النظام الإداري الحالي، تنفيذًا فعليًا لا توصيات.

## 0. المحرك الجاهز (لا تكتبه من الصفر)
- المصدر: `~/.claude/skills/dheeban-toolbox/timetable/` (إن لم يوجد: مستودع `alaoufi/agent99`، المسار `skills/dheeban-toolbox/timetable/`؛ إن تعذّر الوصول فاطلب من المالك إرفاق agent99 بالجلسة).
- فيه `engine.py` (solve/check/diagnose/views) و`test_engine.py` (13 اختبارًا ناجحًا) و`README.md` (شكل المدخلات والمخرجات). الإصدار المثبت: `ortools==9.15.6755`.
- انسخ `engine.py` إلى المشروع في وحدة مستقلة (مثل `scheduling/engine.py`) وأضف `ortools==9.15.6755` إلى تبعيات المشروع. إن كان المشروع بغير Python فشغّل المحرك خدمةً/عملية Python جانبية يستدعيها النظام بـ JSON.

## 1. قبل أي تعديل
1. أنشئ نقطة تراجع: فرع `backup/<التاريخ>-before-timetable` مدفوع + نسخة احتياطية كاملة لقاعدة البيانات (pg_dump أو ما يناسب) واذكر اسمها وطريقة الاستعادة.
2. افحص بنية المشروع وقاعدة البيانات الفعلية: جداول المعلمين والمواد والفصول والطلاب والحصص/الجدول الحالي والتخصصات والنصاب والتوفر. اكتب خريطة الربط (حقل القاعدة ← مفتاح المحرك) في `docs/scheduling.md` قبل الكود.
3. لا تنشئ قاعدة بيانات موازية ولا جداول مكررة. أضف فقط ما ينقص فعلًا (مثلًا: إصدارات الجدول وحالته «مسودة/معتمد/منشور») عبر migration قابلة للتراجع، وبعد عرض المقترح.

## 2. الربط
- محوّل `to_engine()` يقرأ من القاعدة ويبني JSON المحرك، و`save_schedule()` يكتب النتيجة في جداول الحصص الموجودة كإصدار «مسودة».
- الشروط الإلزامية والمرنة كما في README المحرك. الدمج (معلم لفصلين بالتزامن) فقط عند تطابق المرحلة والمادة وموضوع الدرس ووفق ضوابط المشروع.
- التوقيت Asia/Riyadh. أيام الدراسة وعدد الحصص من إعدادات النظام لا ثابتة في الكود.
- لا يُرخى أي شرط إلزامي تلقائيًا. التشخيص يُعرض للإدارة بالعربية مع الاقتراحات.
- حساب الجدول والتعارضات بالمحرك دائمًا، لا بالذكاء الاصطناعي.

## 3. واجهة الإدارة (بمهارات ui-ux-pro-max وfrontend-design، وبنفس تصميم النظام الحالي)
إنشاء آلي · فحص التعارضات · تحسين · إعادة جدولة جزئية (اختيار الوحدات المحررة) · تعديل يدوي بسحب وإفلات مع `check` فوري · معاينة جدول كل معلم وفصل وطالب · اعتماد قبل النشر · إصدارات سابقة مع استعادة.
- كل نص يظهر للمستخدم يُضاف لـ«نصوص الموقع» في لوحة الإدارة، لا ثابتًا في الكود (بما فيها رسائل التشخيص: اجعلها مفاتيح قابلة للتعديل مع النص الافتراضي من المحرك).
- لا يظهر جدول للطلاب والمعلمين إلا بعد اعتماد الإدارة.
- الإنشاء والتحسين في مهمة خلفية (قد يأخذ حتى time_limit)، مع عرض أول حل صالح فورًا.

## 4. الاختبارات (test-driven-development)
1. شغّل `test_engine.py` كما هو في المشروع.
2. اختبارات المحوّل والحفظ والإصدارات والاعتماد والواجهة.
3. نسخة من بيانات المشروع الفعلية في بيئة آمنة (لا الإنتاج): قِس الزمن وأول حل والذاكرة والمعالج، وتأكد من 0 تعارض.
4. تأكد أن كل الوظائف والاختبارات الحالية ما زالت تنجح.

## 5. الاستخدام الدائم
- وثّق في `AGENTS.md` و`docs/scheduling.md`: «كل مهمة جدولة أو فحص تعارض حصص تستخدم محرك CP-SAT إلزاميًا»، وطريقة التشغيل وإضافة شرط جديد (دالة في `Model._build` + اختبار).
- نسّق مع وكيل الفصل الدراسي (حسب AGENTS.md للمشروع) قبل تغيير أي واجهة يقرأ منها الجدول، وسجّل الاتفاق في الوثيقة.

## 6. التقرير للمالك (بالعربية)
نتائج الاختبارات، سرعة الجدولة (أول حل والإجمالي) والموارد، التعارضات المكتشفة في البيانات الفعلية وأسبابها، الملفات المعدلة، طريقة الاستخدام، ونقطة التراجع وطريقة الاستعادة (الكود والقاعدة).
